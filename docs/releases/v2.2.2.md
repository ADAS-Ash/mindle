**Mindle 2.2.2** — two stability fixes to the annotation sidebar's text rendering. No new features.

## What's fixed

### Crash on wrapped annotation bodies

Hitting a particular pattern in the sidebar — most reliably an annotation body that wraps to enough lines that its laid-out glyphs exceed the initial frame height — could crash the app with `EXC_BREAKPOINT` during AppKit's draw cycle. Root cause was the `SelectableText` host view (added in v2.2.0 by [PR #30](https://github.com/nonatofabio/mindle/pull/30)) shipping with `isVerticallyResizable = true`. When the inner `NSTextView` discovered mid-`drawRect` that its frame wasn't tall enough, it called `_resizeTextViewForTextContainer → setFrameSize`, which cascaded through the autoresizing-into-constraints layer into SwiftUI's host `invalidateLayout`. AppKit forbids constraint changes during a draw transaction and crashes the app rather than swallow the exception.

Latent since v2.2.0 — rare enough on the markdown annotations the PR was tested against that nobody hit it, far more common on multi-line selections. The fix is to disable the text view's self-resize entirely; the host (`SelectableTextHostView`) is the sole authority on height. Text that somehow exceeds the host's reported height now clips rather than crashing.

### Annotation bodies no longer overlap the action row

A separate sizing bug in the same view: `SelectableText` relied on `intrinsicContentSize`, which SwiftUI queries before the first layout pass — at which point `bounds.width` is still 0 and the host returned a one-line height. SwiftUI used that to position the siblings below, then the actual multi-line text rendered into the same Y range as the Resolve / Assign row, so the buttons appeared *behind* the wrapped body.

Adds the macOS 13+ `sizeThatFits(_:nsView:context:)` hook so SwiftUI gets the wrap-aware height up front, before placing siblings. The existing `intrinsicContentSize` path stays as a fallback for any AppKit-driven layout that doesn't go through SwiftUI's sizing protocol.
